# Measurement gate (G1) — decision record

**Date:** 2026-07-24
**Commit:** `f901bb5` (A1 live on all three edges)
**Decision:** **DEFER Part B (QUIC).** A2 is not demonstrated to be a practical
problem for this deployment after A1. No QUIC changes.

This is a **judgment-based deferral**, not a completed G1 measurement showing A2
absent. Stated plainly so no one later mistakes it for a measured no-go.

## Status of the gate

- **Harness: built and correct.** `test/perf/perfserver`, `test/perf/perfclient`
  (ordered raw TTFB/elapsed samples), `test/perf/analyze.py` (fails closed —
  INCONCLUSIVE + nonzero exit on missing cases / too few samples / any
  errors/corruption, multi-rung TTFB ladder required, and a clean-control guard
  that rejects artifacts), `scripts/perf-g1.sh` + `scripts/perf-g1-agent.sh`
  (real-edge runner: shaped container agent against a real remote edge, netem
  applied **before** the agent dials, unshaped host public leg). This addresses
  every finding from the code review of the earlier synthetic harness.
- **Real-edge run: NOT completed.** A clean run needs a reachable dedicated test
  edge. The OSS box's :8443 is firewalled externally (ufw allows only
  22/2375/2376; the live edge on :443 works only via Docker's DNAT bypass) and
  its SSH began rate-limiting/refusing after repeated connections. The only
  friction-free alternative was to run against **production** (`beamd.run`),
  which perf-loads the live edge and mints a throwaway Let's Encrypt cert on the
  prod domain — not warranted for a single-user go/no-go.

## Why deferral is the right call here

1. **A1 already delivered the real-world win.** The operator reported the app is
   "much snappier" after A1 on their real network — i.e. their actual pain was
   window-limited (A1's domain), not the A2 loss-recovery pattern.
2. **A2 only bites on lossy / high-RTT links.** It is a real property of a single
   multiplexed TCP connection (a lone stream recovers from loss poorly while the
   connection idles; parallel streams keep it ACK-clocked). It shows up under
   packet loss, which good wired/broadband paths rarely have. There is no
   evidence this single user regularly tunnels from such networks.
3. **QUIC is a large, speculative build** (a transport abstraction, a QUIC
   engine, key lifecycle, selection/fallback, capacity, and a qualification
   suite — ~15 files, a new UDP transport, ongoing maintenance) for one happy
   user, to fix a symptom not shown to occur in practice.

Per spec §16 G1.6, mark **B1–B4 "not currently justified."**

## Reopen criteria

Run the committed harness against a real edge (open a dedicated test-edge port,
or accept a bounded run against prod) and record a measured verdict if:

- the operator begins tunneling regularly from lossy/high-RTT networks (mobile
  hotspots, cafe wifi) and notices solo transfers stalling; or
- a second user / higher concurrency changes the calculus; or
- there is appetite to make the measured go/no-go rigorous regardless.

The harness is ready; only a reachable edge + a token are needed.
