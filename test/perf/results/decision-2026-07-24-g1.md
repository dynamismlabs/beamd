# Measurement gate — decision record (revised)

**Date:** 2026-07-24
**Commit:** `f901bb5` (A1 live on all three edges)
**Decision:** **GO — build Part B (QUIC), behind the default-off flag.**
Reverses the earlier same-day deferral after a second test measured a severe,
real problem the first test missed. Pending operator greenlight (Part B is weeks
of work); the evidence justifies starting it.

The two tests measured **different axes**, and only the second matches the
"many users on one app" scenario:

## Axis 1 — bulk throughput (original G1 solo-vs-parallel): no problem

Data: `g1-local-2026-07-24/`. Under loss a solo transfer gets ~97% of the
8-stream aggregate; no 1/2/4 s timeout ladder. Bulk throughput is fine on the
shared connection. This finding stands — it just isn't the axis that hurts.

## Axis 2 — interactive latency under mixed load (HoL): SEVERE

Data: `hol-2026-07-24/`. All app traffic multiplexes over **one** edge↔agent
TCP connection. A latency-sensitive request measured **alone vs. under a bulk
load** of 6 concurrent "visitors" on that same tunnel:

| Connection | 4 KB alone (p95) | 4 KB under load (p95) | inflation |
| --- | ---: | ---: | ---: |
| clean (no loss) | 42 ms | 415 ms | 10× |
| wifi (40 ms/1%) | 96 ms | 1.7 s | 18× |
| mobile (150 ms/2%) | 314 ms | 7.7 s | 24× |
| bursty (60 ms/2% corr) | 71 ms | 2.7 s | 38× |

A 4 KB API call needs ~2 ms of bandwidth, so this is **not** bandwidth
starvation — it is the interactive response **queued behind bulk bytes on the
single shared connection**: bufferbloat with no loss, TCP head-of-line blocking
with loss (one lost packet stalls every stream behind it). This is precisely the
"no TCP head-of-line blocking between independent streams" benefit QUIC is cited
for in §2, and it degrades catastrophically on exactly the lossy/mobile links a
real user base hits.

**Conclusion:** the shared single TCP tunnel is a real, severe UX risk for a
busy multi-user app, and QUIC's independent per-stream delivery is the direct
structural fix. Building Part B (behind the flag) is justified.

## Honest caveats (do not skip these)

- **QUIC's fix is expected, not yet measured.** It is the textbook remedy and is
  in the spec's own rationale, but the *actual* improvement must be proven by the
  Part B qualification (B4) before the default is flipped. G1 justifies building;
  B4 justifies defaulting.
- **Load-dependent.** 6 concurrent bulk streams is "busy, not extreme"; the
  effect is smaller under lighter load but present whenever any bulk shares the
  tunnel with interactive traffic.
- **Controlled reproduction**, not the production WAN (mechanism is faithful; a
  real WAN would be similar or worse).
- **A1 interaction / cheaper partial mitigation.** Part of the *no-loss* 10×
  (bufferbloat) is send-side queuing that the 4 MiB A1 window enlarged; tuning
  buffers or adding yamux stream prioritization could reduce the clean case
  *without* QUIC. But that does **not** fix the loss-driven HoL on wifi/mobile
  (the worst cases), which is fundamental to one in-order TCP connection. Worth a
  quick experiment, but not a substitute for Part B.

## Recommendation / next step

Greenlight **Part B behind the default-off flag** (§16 Changes 1–4): abstraction
→ QUIC engine (default off) → selection/flags/diagnostics → deploy + **B4
qualification**, and flip the default to QUIC only if B4 shows it actually cuts
the under-load interactive tail without regressing the clean path. Optionally,
first spend an hour on the buffer/prioritization experiment to see how much of
the no-loss case is cheaply recoverable.
